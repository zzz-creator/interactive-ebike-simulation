Council Report — What should we add?

Question: Interactive e-bike drivetrain & regenerative braking HTML sim. "What should we add?"

Seated: Core five (Contrarian, First Principles, Expansionist, Outsider, Executor) + panel (Innovator, Pragmatist, Risk Assessor, Strategist).

Chairman's Verdict

Where the Council Agrees

  • The fatal defect is real and unanimous: regenerative braking is advertised as the lab's headline, yet the hold-to-brake control was just removed and state.isBraking has no UI toggle. Every advisor converged on this; Outsider and Executor quantified it at ~30 lines. Fixing this is non-negotiable before anything else.
  • Avoid list consistent: no 3D, no accounts/backend/multiplayer, no gamification beyond simple scoring, no extra gears/visual polish, no audio (majority), no more controls without removing others. Cognitive load is the binding constraint.
  • Quantitative readouts are table stakes: watts in/out, Wh recovered, efficiency %, and a conservation overlay. The sim must change what a learner concludes, not just what they see.
  • Shareable URL state + localStorage presets universally endorsed (Executor, Pragmatist, Strategist) as the highest-leverage distribution move.
  • The app has no failure containment: single-file canvas, rAF loop dies silently. Risk Assessor's error boundary + numeric guards agreed necessary.
  • Model correctness is unvalidated — surfaced in peer review by all five reviewers. Nobody has checked the drivetrain/regen numbers against real e-bike specs.

Where the Council Clashes

  • Monetization vs. pedagogy: Expansionist wants GPX importer and fleet TCO calculator as a monetizable wedge now; Contrarian, First Principles, and every peer reviewer flagged building a revenue layer on an unvalidated physics model. Council does not support shipping monetization before the core teaches correctly.
  • Scope ordering: Executor wants exactly three tightly scoped ship items (brake lever, battery clamp, URL state); Risk Assessor wants reliability/a11y hardening first; Pragmatist wants URL state → presets → keyboard → tour → CSV → reduced-motion. Differ on whether to ship features or harden first.
  • Audio: Outsider and Innovator want Web Audio motor whine/regen hum; Contrarian and Executor explicitly skip it. Split verdict — defer unless trivial and behind a toggle.
  • More physics modes: First Principles and Innovator want thermal derating, failure states (BMS cutoff, regen at full charge), cold-soak; Strategist says don't add more physics modes, the moat is distribution. Resolution: add failure-mode states (they teach), not new physics modes (they don't).

Blind Spots the Council Caught

  • Physics model validation — no one checked drivetrain/regen numbers against real measurements; no calibration, no documented assumptions.
  • Instructor/educator workflow — presets, reset, guided tour, embeddable widget mode, "does it teach" evaluation criteria.
  • Accessibility — colorblind-safe palette, reduced-motion, keyboard parity, ARIA live region for motor state, touch parity.
  • Mobile/touch responsiveness and viewport fit on small screens.
  • README/assumptions documentation and unit localization (metric/imperial).
  • Concrete acceptance test / baseline metric — no one defined "done" or how to measure teaching efficacy.
  • Scope-risk ranking — which additions risk breaking the single-file architecture.
  • rAF failure containment — silent crash with no recovery or user feedback.

The Recommendation

  1. Restore the regen brake control — hold-to-brake button + 0–100% slider + Space key, wired to existing state.isBraking/regenForce. ~30 lines. Unblocks the entire lab.
  2. Quantitative readouts + conservation overlay — watts in/out, Wh recovered, efficiency %, energy-budget ledger. Makes it a lab, not an animation.
  3. Failure-mode states — BMS cutoff, regen zeroed at full charge ("BATTERY FULL"), chain slip. ~5 lines for the overcharge guard alone.
  4. Shareable URL state + 3 localStorage presets — distribution foundation.
  5. Error boundary + numeric guards — try/catch around updatePhysics/drawBike, visible "simulation paused" banner, rAF restart, clamped angular velocity, min dt floor, SOC persisted to localStorage.
  6. Accessibility pass — keyboard controls, ARIA live region, reduced-motion respect, touch parity.
  7. Validate the physics model against real e-bike specs and document assumptions in a README before any expansion or monetization.

Explicitly avoid: 3D, audio (unless trivially toggleable), accounts/backend, multiplayer, GPX/fleet TCO until core is validated, more gears, visual polish, gamification beyond simple scoring, and any feature that doesn't change a student's conclusion.

The One Thing to Do First

Restore the regen brake control — a hold-to-brake button plus a 0–100% slider and Space-key binding, wired to the already-present state.isBraking and regenForce. The headline feature of this lab is currently unreachable; every other addition is moot until a learner can actually brake and recover energy.

Advisor Responses

The Contrarian
The fatal flaw is that you just removed the one interaction that makes regenerative braking *real* — the hold-to-brake button is where students actually see energy reverse direction. Without it, this is a drivetrain animation, not a regen lab. Add it back, or add a slider-controlled braking torque that shows the same reversal with a tunable parameter.

What to add that earns its keep: quantitative readouts (watts in/out, Wh recovered, motor efficiency at current RPM), a grade selector with real percentages (0–15%), and a side-by-side comparison mode (direct-drive vs. geared) so the chain bypass actually demonstrates something. Also add a "sanity check" overlay showing whether current energy flow violates conservation — it turns the canvas from eye candy into a verifiable instrument.

What to avoid: 3D rendering, audio, particle trails beyond 50 elements, gamification, leaderboards, user accounts, or any feature requiring a backend. Every one of those delays the core question students ask — "where did the energy go?" — and none of them answer it. The lab's value is pedagogical clarity, not spectacle. If a feature doesn't make the physics more legible, cut it. Also avoid adding more controls without removing others; the viewport is already full, and cognitive load is the real constraint, not screen space.
The First Principles Thinker
The real question isn't "what features are missing" — it's "what must a learner understand about this drivetrain that the current model doesn't yet make visible." The sim already teaches flow: pedal→battery, battery→motor, wheel→battery via regen. What it doesn't yet surface is *cost*: where energy is lost, how efficiency varies, and what the trade-offs actually feel like.

Add (high leverage): per-component efficiency readout (motor, drivetrain, regen) so students see that regen recovers only a fraction, not 100%. Thermal / current-limit indicators — real e-bikes derate; showing "motor overheating, assist reduced" teaches real constraints. A scenario mode (flat commute vs. steep climb vs. descent) with summary: Wh consumed, Wh recovered, net battery delta. Failure-mode states: battery BMS cutoff, regen disabled at full charge, chain slip. Energy-budget ledger (cumulative Wh in/out per source).

Avoid: 3D rendering, richer graphics, animation polish; gamification (scores, badges, sharing); more input controls without a corresponding insight; features implying precision the model doesn't have; anything requiring accounts, servers, or persistence.

The discipline: every addition must change what a student *concludes* about energy, not just what they *see*.
The Expansionist
The sim as-is is a physics toy. The bigger play is turning it into a decision engine for real money and real commutes.

Adjacent opportunities being undervalued: GPX import / real-route mode (drop actual commute GPX, see regen yield, battery SOC curve, time delta on their hills — purchase-justification tool). Fleet & TCO calculator (e-bike vs car vs transit over 1/3/5 years). Battery aging model (cycle count, depth-of-discharge, temperature — makes regen tradeoff honest). Shareable "my ride" cards (PNG/URL of efficiency score). Motor/gearing sandbox (swap hub vs mid-drive).

Don't bother with: 3D rendering, multiplayer, accounts. The upside is in specificity of real-world application, not polish. Ship GPX importer first — it's the wedge that makes everything else monetizable.
The Outsider
From a cold read, the most glaring gap: regenerative braking is advertised everywhere (header, callout, legend) but there is no brake control in the UI. state.isBraking exists in JS, yet nothing in the HTML toggles it — a first-time user cannot trigger the headline feature at all. Add a prominent brake button (hold-to-brake, plus a keyboard shortcut like Space) and wire it to isBraking.

Other first-impression gaps: No onboarding (first-run overlay). No reset/stop (zero speed). No keyboard controls. No audio. No comparison mode (A/B view). No data export (CSV/JSON dump).

Prioritize the brake button — it's the feature the whole sim is named around and it's currently unreachable.
The Executor
Monday morning, ship these three, in this order:

1. Regen brake lever (the actual missing control). Section 3 only has grade presets — no brake input, even though physics references "New Force" regen braking. Add a 0–100% brake slider next to grade buttons that sets state.isBraking and feeds regenForce. Effort ~30 lines.
2. Battery clamp + overcharge guard. Nothing stops SOC from exceeding 100% during downhill + pedaling. Add Math.min(100, ...) and a visual "BATTERY FULL — regen disabled" state that zeros out wattsHubRegen. Effort 5 lines.
3. Persisted shareable URL. Encode grade, gear, mode, autoPedal into query params; read on load. No backend, ~20 lines.

Skip for now: cadence-based gear shifting animation, mobile touch polish, audio, multi-bike comparison.
The Innovator
The Innovator's picks: Regen "dead zone" + strength dial (real hubs don't regen below ~8 km/h; add regen-strength slider and low-speed cutoff). Cold-soak battery derating (temperature slider). Ghost-bike A/B overlay (second translucent bike running pure mechanical chain-drive alongside hybrid, plot cumulative Wh consumed). Energy-budget challenge mode (fixed battery + target distance, score by kWh/100km). Web Audio motor whine + regen hum. URL-state export.

Skip: more gears, prettier wheels, extra telemetry badges — polish, not insight.
The Pragmatist
Ship small, self-contained wins — no backend, no new deps, no framework swap.

High value, low effort: URL state for scenarios (~30 lines). localStorage presets (3 slots). Keyboard + touch parity. Guided 60-second tour. CSV export of telemetry. Reduced-motion + "demo mode" reset.

Defer: 3D/WebGL, multi-bike comparison, physics-engine swap, accounts, leaderboards. Also don't add testing framework unless splitting script.js into modules.

Order of attack: URL state → presets → keyboard → tour → CSV → reduced-motion. Each independently shippable in an afternoon; none blocks the others. Stop after CSV unless user research says otherwise.
The Risk Assessor
Risk: single-file canvas app with no failure containment. Pre-mortem: one bad frame or null element and the whole rAF loop dies silently. Add try/catch around updatePhysics/drawBike plus visible "simulation paused — reload" banner, and rAF restart guard.

Second risk: physics has no tripwires. wheelAngularVel can spike; socDelta misleading due to dt ~0 on tab-switch. Add clamps (max angular velocity, min dt floor 1/120) and guard that snaps to last-good state instead of NaN-propagating.

Third: no accessibility/fallback. Canvas-only means screen readers get nothing and keyboard users can't pedal. Add ARIA live region for motor state + keyboard controls.

Fourth: battery SOC no hysteresis — at 0.2% motor cuts hard with no warning. Add "low battery" tripwire at 10% with confirm-style modal before assist disables, persist SOC to localStorage.

Mitigation order: error boundary first, then numeric guards, then a11y, then persistence.
The Strategist
Strategic read: single-file demos don't compound. 2-5 year play is to make it the canonical, embeddable reference for e-bike drivetrain education.

Priority: 1. Shareable scenario URLs. 2. Preset challenges + scoring. 3. Embeddable widget mode (?embed=1). 4. Telemetry export (CSV + screenshot). 5. PWA/offline + mobile touch polish.

Don't add: more physics modes, 3D, multiplayer. Moat is distribution and habit, not fidelity.

The game: own "e-bike drivetrain, explained" as a search term and embed.
